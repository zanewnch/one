# Java RAG 專案引導式作業

透過實作高併發 RAG 知識庫問答服務，學習 Java、Spring 與系統設計。你負責寫程式與說明方法，Codex 負責出題、提供提示及 review；每份作業的成果會成為專案的一部分。

Assignment 說明要學什麼、怎麼開始；ticket 定義需求範圍與完成條件。這裡結合兩種方式，讓你知道下一步要做什麼，也能判斷是否完成。專案的目標架構見[專案 README](../README.md)。

## 每份作業的固定格式

| 區段 | 你會得到的內容 |
| --- | --- |
| 情境與目標 | 功能解決什麼問題，以及如何接到 RAG 流程 |
| 學習重點 | 必要概念與簡短 C# 對照 |
| 任務範圍 | 本次輸入、輸出、責任邊界與不需完成的功能 |
| 步驟提示 | 分步方向與查閱位置，保留實作空間 |
| 驗收條件 | 具體成功結果、邊界與失敗案例 |
| 方法說明 | 交付程式、測試結果與設計理由的要求 |

後續出題沿用[作業模板](assignment-template.md)，並先核對當時的程式與上一份成果。以最小可驗收功能出題，不為尚未確認的需求預先增加框架或服務。

## 實作與 review 流程

1. 先閱讀本次情境、契約與驗收條件，畫出或描述資料流。
2. 依步驟提示實作；卡住時附上檔案、程式片段、錯誤及嘗試過的方法。
3. Codex 先給最小提示；你明確要求某一部分的完整範例時，才展開該部分程式。
4. 交付修改檔案、執行命令與結果，以及方法說明；不能只貼「BUILD SUCCESSFUL」。
5. 你請求驗收後，Codex 讀取實際程式或 diff，對照資料與條件 review，執行必要的相關檢查並說明具體問題。
6. 修正後再次核對；功能符合條件且你能解釋方法時，才標記完成並出下一份作業。

程式、測試通過與你是否理解方法分別判斷。未執行的檢查不能列為已通過，作業文件建立也不代表作業已完成。

## 協作預設

- 程式由你實作；出題與 review 不直接替你改檔。明確指定代寫的部分時，才調整協作方式。
- 一次只展開一份詳細作業；其餘保留階段目標。
- 第一階段不接模型、不做併發，也不改現有 benchmark 的量測語意。
- 資料集保留原檔與授權，測試使用小型 fixture；不將憑證或個人設定提交到 Git。
- 效能作業先建立基線，再用相同負載比較；不預設吞吐量或延遲承諾。
